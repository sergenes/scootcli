# 0.4.0 plan: hooks and headless mode

Two standard surfaces that let other programs drive and observe scoot without scraping its terminal.
Both are provider-independent and change nothing for interactive use.
What ships is specified in `SPEC.md` once done; this file is the plan.

## Why

A coding agent gets embedded: in editors, in automation, in remote-control tools, in CI.
Today the only machine interface is `--json` one-shot mode, which covers a single turn and offers no approvals.
The two features below are the shapes the ecosystem has converged on: hook scripts fired on lifecycle events, and a line-delimited JSON protocol over stdin and stdout.

## Part 1: hooks

Shell commands that scoot runs at lifecycle points, receiving a JSON payload on stdin and answering with an exit code or a JSON decision on stdout.
The payload shapes follow the de-facto standard set by Claude Code so existing hook scripts work with scoot with little or no change.

### Events

| event | when | payload fields beyond the common ones | can block? |
|---|---|---|---|
| `SessionStart` | REPL or one-shot begins, and on `/reset` | `source`: `startup` \| `resume` \| `reset` | no |
| `UserPromptSubmit` | a prompt is accepted, before the model sees it | `prompt` | yes: exit 2 or `{"decision": "block"}` drops the prompt; stdout text is added as context |
| `PreToolUse` | before a tool runs, after scoot's own approval logic decided to run it | `tool_name`, `tool_input` | yes: `{"permissionDecision": "allow" \| "deny" \| "ask", "reason": ...}`; exit 2 denies |
| `PostToolUse` | after a tool ran | `tool_name`, `tool_input`, `tool_response` (`ok`, `summary`, `content` bounded) | no |
| `Stop` | the assistant finished a turn | `last_assistant_message`, `steps`, `usage` | yes: `{"decision": "block", "reason": ...}` makes scoot continue with the reason as a user message |
| `Notification` | scoot needs the user: approval prompt shown, step limit reached, error surfaced | `message`, `kind` | no |
| `SessionEnd` | REPL exits or one-shot completes | `reason` | no |

Common fields: `session_id`, `cwd`, `hook_event_name`, `model` (qualified), `transcript_path` (the saved session file).
Tool names are scoot's (`read_file`, `edit_file`, `run_shell`, ...); the payload also carries `tool_kind` (`read` \| `write` \| `shell` \| `meta`) so a script can match by class instead of by name.

### Configuration

`hooks.json` in `~/.config/scoot/` (global) and `.scoot/hooks.json` in the workspace (project), merged, project first.
Same structure as Claude Code's `hooks` block, so a file can be shared between the tools:

```json
{
  "PreToolUse": [
    {"matcher": "run_shell|write_file|edit_file", "hooks": [{"type": "command", "command": "~/bin/approve.py", "timeout": 120}]}
  ],
  "Stop": [
    {"hooks": [{"type": "command", "command": "~/bin/notify.sh"}]}
  ]
}
```

`matcher` is a regex on `tool_name` (PreToolUse and PostToolUse only); absent means all.
`timeout` in seconds, default 60; a hook that times out is treated as "no decision" and logged.
`SCOOT_HOOKS=0` disables all hooks for a run; `/hooks` lists what is configured and the last result of each.

### Rules

- Hooks run with `cwd` set to the workspace root, the payload on stdin, and `SCOOT_SESSION_ID` plus `SCOOT_HOOK_EVENT` in the environment.
- Exit 0 with empty stdout: no decision. Exit 0 with JSON stdout: the decision. Exit 2: block, stderr is the reason. Any other exit: logged, ignored.
- A `PreToolUse` `deny` is fed back to the model as a tool result (`user declined via hook: <reason>`), the same path as a manual skip, so the loop continues.
- `ask` from a hook forces scoot's own approval prompt even in `yolo` mode.
- Hooks never see API keys; the payload carries no configuration.
- Hooks run sequentially in configuration order; the first blocking decision wins.
- One-shot and headless modes fire the same events.

### Implementation

- `scootcli/hooks.py`: config loading and merging, `run_hooks(event, payload) -> Decision`, subprocess with timeout and the cancel event, bounded stdout/stderr capture.
- Call sites: `repl.py` (SessionStart, UserPromptSubmit, Stop, SessionEnd, Notification), `agent.py` (PreToolUse after `needs_prompt`, PostToolUse after `_handle_result`).
- `commands/hooks.py`: `/hooks` listing.
- Tests: a fake hook script per outcome (allow, deny, ask, block-with-reason, timeout, crash, bad JSON), matcher semantics, merge order, the deny-to-tool-result path, `SCOOT_HOOKS=0`.

## Part 2: headless mode

`scoot --headless`: a long-lived process that speaks line-delimited JSON on stdin and stdout, one object per line, nothing else on stdout.
Logs and diagnostics go to stderr.
It is the multi-turn form of `--json`; sessions, compaction, tools, and hooks all work as in the REPL.

### Input (stdin, one JSON object per line)

| type | fields | effect |
|---|---|---|
| `prompt` | `text`, optional `images` (paths) | starts a turn |
| `approve` | `id`, `decision`: `allow` \| `deny` \| `allow_tool` \| `allow_session` \| `abort`, optional `args` | answers an `approval_request` |
| `note` | `text` | queued and delivered as extra user context at the next model call of the running turn |
| `interrupt` | | cancels the running turn (what ESC does) |
| `command` | `name`, `args` | runs a slash command (`compact`, `model`, `reset`, `status`, ...) |
| `shutdown` | | saves the session and exits 0 |

### Output (stdout, one JSON object per line)

| type | fields |
|---|---|
| `ready` | `session_id`, `model`, `version`, `cwd`, `tools` |
| `turn_start` | `turn`, `prompt` |
| `text_delta` | `text` (streamed answer fragments) |
| `assistant` | `text` (complete narration or answer), `final`: bool |
| `tool_call` | `id`, `name`, `args`, `kind`, `auto_approved`: bool |
| `approval_request` | `id`, `name`, `args`, `kind`, `preview`, `options` (the same six choices the REPL offers), `timeout_s` |
| `tool_result` | `id`, `name`, `ok`, `summary`, `content` (bounded) |
| `plan` | `steps` (from `update_plan`) |
| `turn_end` | `status`, `steps`, `model`, `usage`, `content` |
| `error` | `message`, `hint`, `kind` |
| `notice` | `message` (compaction, model fallback, step-limit reached) |
| `heartbeat` | `busy`: bool, every 10 s while a turn runs |
| `bye` | on shutdown |

### Rules

- Approval requests come from the same decision path as the REPL; in headless mode the prompt is an event, and an unanswered request denies after `SCOOT_APPROVAL_TIMEOUT` seconds (default 120).
- `SCOOT_APPROVAL=yolo` still auto-approves; the denylist still produces an `approval_request` that must be answered.
- Reaching the step limit emits `notice` and ends the turn with `status: max_steps`; the caller decides whether to send another prompt.
- Output is never coloured and never contains ANSI sequences.
- The protocol is versioned in `ready.protocol` starting at `1`; fields are only added, never renamed, within a major version.

### Implementation

- `scootcli/headless.py`: the reader thread for stdin, the event writer with a lock, a `HeadlessUI` implementing the same UI protocol the agent already calls (`activity`, `stream`, `approve`, `assistant`, `plan`, `tool_result`) plus the approval wait with timeout.
- `cli.py`: `--headless` flag; mutually exclusive with a prompt argument.
- Reuse: `ReplSession`, `Agent`, `sessions`, `hooks`. No new agent logic.
- Tests: a scripted provider drives full turns through the protocol; approval round trip; `note` delivery; `interrupt`; timeout deny; malformed input lines are reported as `error` and skipped; stdout contains only JSON lines.
