# Plan: 0.13.0

Status: proposed, not started. 2026-09-10.
This file describes the planned 0.13.0 work in enough detail to assess its effect on anything that drives scoot, in particular the agents-at-work bridge.
What ships is specified in `SPEC.md` once done; this is the plan.

0.13.0 finishes the outside review with its last two corrections, both deferred from 0.12.0 because each can affect the bridge.
Neither adds a tool, a provider, or a headless protocol event.
There is also one optional feature candidate, `fetch_url`, kept separate.

## Item A: one config-directory resolver

### The problem

scoot resolves its config directory four different ways today:

- Project and global `.env` (`config._config_home`): `XDG_CONFIG_HOME/scoot` if `XDG_CONFIG_HOME` is set, else `~/.config/scoot`. Does not consult the `SCOOT_CONFIG_DIR` environment variable.
- Hooks (`hooks.global_path`): the `SCOOT_CONFIG_DIR` environment variable if set, else `XDG_CONFIG_HOME/scoot`, else `~/.config/scoot`.
- Saved credentials (`credentials._file`): the `SCOOT_CONFIG_DIR` environment variable if set, else a hard-coded `~/.config/scoot`. Ignores `XDG_CONFIG_HOME`.
- Preferences (`preferences._config_dir`): same as credentials.

So `XDG_CONFIG_HOME` moves the `.env` and hooks locations but not credentials or preferences, and only hooks and credentials honor the `SCOOT_CONFIG_DIR` variable.

### The change

Introduce one resolver used everywhere, with this precedence:

1. `SCOOT_CONFIG_DIR` environment variable, if set.
2. else `XDG_CONFIG_HOME/scoot`, if `XDG_CONFIG_HOME` is set.
3. else `~/.config/scoot`.

This is exactly the rule hooks already use.
Apply it to `.env`, hooks, credentials, and preferences.

### What changes in behavior

- **Hooks path: unchanged in every case.** Hooks already use this precedence, so the resolved `hooks.json` path does not move whether the environment sets `SCOOT_CONFIG_DIR`, sets `XDG_CONFIG_HOME`, or sets neither. This is the property the bridge depends on.
- **Credentials and preferences: change only when `XDG_CONFIG_HOME` is set and `SCOOT_CONFIG_DIR` is not.** In that case they move from `~/.config/scoot` to `XDG_CONFIG_HOME/scoot`. With neither variable set, or with `SCOOT_CONFIG_DIR` set, their location is unchanged.
- **`.env`: gains `SCOOT_CONFIG_DIR` support.** A user who set `SCOOT_CONFIG_DIR` will now have their global `.env` read from there too.

### Compatibility measure

To avoid making a user with `XDG_CONFIG_HOME` re-authenticate, credentials and preferences will fall back to reading the legacy `~/.config/scoot` location when nothing is found at the new resolved path, and write to the new path.
The net effect is that existing saved keys keep working and migrate on the next write.

### Files

`config.py` (the resolver and the `.env` paths), `hooks.py`, `credentials.py`, `preferences.py`.

### What the agents-at-work agent should verify

- With the bridge's exact environment, whatever `SCOOT_CONFIG_DIR` and `XDG_CONFIG_HOME` are set to, the resolved global `hooks.json` path is identical before and after, and the bridge's installed hook still fires on `SessionStart` and `PreToolUse`.
- If the bridge sets `XDG_CONFIG_HOME`, saved credentials still resolve, either at the new path or via the legacy fallback, so no re-auth is needed.
- If the bridge sets `SCOOT_CONFIG_DIR`, everything (`.env`, hooks, keys, preferences) now resolves under that one directory, which is the intended, consistent behavior.

## Item B: proactive, shared compaction

### The problem

Compaction runs today only after an interactive REPL turn, when the context estimate passes `SCOOT_COMPACT_AT`.
Headless and one-shot mode never compact.
A single very large turn can therefore exceed the model's context window with no compaction, and a reactive compaction can itself be too large to send.

### The change

Add a context check before each model request in the shared agent loop, so it runs the same way in the REPL, headless, and one-shot.
When the estimated context exceeds the threshold, summarize the older messages, preserve the most recent turns verbatim, and bound the amount of older text sent for summarization.

### What changes in behavior

- **Headless and one-shot now compact.** A large request triggers a summarization model call before the main call.
- **Extra latency and an extra provider call.** That summarization call adds a round-trip and, since 0.12.0 accounts every call, its tokens and cost are included in the turn's usage and the session totals.
- **`session.messages` is rewritten** when compaction runs: older messages are replaced by a summary. Anything mirroring the message list sees it shrink.

### Files

`context.py`, `agent.py` (the pre-request check), `repl.py`, `headless.py`.

### What the agents-at-work agent should verify

- A turn that triggers proactive compaction still completes and emits a normal `turn_end`; the bridge tolerates the extra latency of the summarization round-trip and does not time out.
- The bridge does not rely on `session.messages` staying the same length within a turn, since compaction shrinks it.
- Larger `turn_end` usage and cost on a compacting turn are acceptable, since the summarization call is now counted (this follows the 0.12.0 accounting change).
- Optional, to be decided during implementation: whether headless should emit a `notice` when proactive compaction runs, so the phone side can show it. If added, it is a new `notice` message, not a new event type.

## Item C, optional: the `fetch_url` tool

A gated, opt-in web-fetch tool, specified in `docs/plans/web-fetch.md`.
It is a feature with real security surface, not a review correction, so it is listed separately and may slip to a later release.
If it lands in 0.13.0, the bridge would see a new `tool_call` and `approval_request` for `fetch_url`, always requiring approval and off by default, so it has no effect unless explicitly enabled.
Decision pending; treat it as not in scope unless confirmed.

## Summary for verification

The only change that can silently break the bridge is Item A, and only if the config-directory path it resolves for hooks moves.
The plan keeps that path identical by adopting the rule hooks already use, so the expected result is no change to the hooks path and no change to the bridge.
Item B changes timing and turn accounting, not interfaces.
Item C is off by default and optional.
No headless protocol version bump and no new event types are planned.
